# 21 October 2026: a progress bar that has to prove itself

<p class="ss-meta">Field note · day 3 · about 8 min</p>

!!! plain "In plain words"
    The home page now has a **Mission readiness** bar, from 0 to 100. It shows how complete and how well built our *plan* is. Today it reads **36**. It is not the chance of finding a planet, and it can't be raised by feeling: every point needs proof, some points are counted by the program itself, and the book refuses to build if the rules are broken.

## What we did, and why

1. **You asked for a progress bar** that updates as we learn and get closer to finding a two-sun planet. The first idea, "how close are we to a planet", can't be measured: a careful search that finds nothing is still a finished plan. So the bar measures the **plan**, and "Candidates found" is a separate counter.
2. **The plan is split into six stages** with points that add up to 100: Know the sky (10), Detector (25), Vetting (20), Calibration (10), The search (25), Candidate to paper (10). Each stage is a list of items with a weight, so you can see exactly what is done and what is not (the [Progress page](../progress.md)).
3. **Three kinds of rule keep it honest:**
    - **No proof, no points.** An item with credit must point to a fact in the claims register or to a file in the repo. If the proof doesn't exist, the book won't build.
    - **Some points count themselves.** "Stars searched out of 549" fills up by itself when the search writes `targets/g1_searched.csv`. "SS-0001 exists" turns on when the first real candidate is added.
    - **Every change is logged.** If I change a credit and forget to write a line saying why, the book won't build. The number can go down if a result is overturned.
4. **The home page status panel is now generated** from the same file, so its numbers can't drift away from the truth the way my hand-typed version did.
5. **A small "Book health" line** shows pages, labs and facts, and counts stale phrases. An en or em dash anywhere in the book now fails the build, because that is your rule.

## The idea behind it

A good progress measure is **checkable**. "We're about 40% there" is an opinion. "These 23 items, with these weights, each with proof, add up to 36" is a statement you can argue with, correct, and watch change. The weights are my first draft; they live in one file (`book/progress/mission.yml`) and you can change any of them.

## How you could do it yourself

Open `book/progress/mission.yml`. To raise a credit: change the number, add the proof, and add one line to `changes` with the date, the points gained and the reason. Then run `.venv-docs\Scripts\python.exe book\tools\test_mission.py` to check the rules, and build the book.

## Questions

??? quiz "1. Why doesn't a bar that fills toward '100 = planet found' make sense?"
    Discovery isn't something we control or can measure in advance. A careful search that finds nothing is still a completed plan, so the bar measures the plan and counts candidates separately.

??? quiz "2. What stops someone from just typing a higher number?"
    Any credit needs proof (a fact or a file that exists), and every change must be logged with a reason that adds up to the total. The book refuses to build otherwise.
