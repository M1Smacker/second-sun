# 3 November 2026: when a frozen version refuses to freeze, believe it, then prove the extra changes do nothing

<p class="ss-meta">Field note · day 16 · about 8 min</p>

!!! plain "In plain words"
    We got the search ready for a third list of stars. The step that freezes a version refused to freeze, because two more code files had changed since the last freeze. We did not override it. We re-ran old results through the new code on three samples of 300 star-sectors each, found two differences, traced them to a limit of our own test (not the code), fixed the test, and only then froze. We also made the text on the phone at least 14 px, and drew a first map of the planets the search could have seen.

## What we did, and why

1. **Prepared the third list for the search (not started).** The search is one-shot: it runs once, on stars it has never seen, with rules fixed first. The code had to learn the new list's file locations, periods, eclipse times and eclipse lengths. These are data paths, not rules.
2. **A fixed table of borrowed good time.** Faint stars often have only one kind of light curve, which needs good-quality time stretches borrowed from neighbouring stars in the same sector and camera. The 612 stars of the third list alone would give almost none (about 1% of cases get a safe borrow). Pooling the three lists gives about 80%. We built that pool once, wrote down its fingerprint, and made the run refuse any other table.
3. **The freeze refused.** The fingerprint covers eleven code files. Five differed from the old freeze: three we had changed on purpose, and two more from switches added on 2 November for a study (they stay off unless asked). We had not noticed that these had already moved the fingerprint.
4. **Proving it, three ways.** The whole chain was re-run on 300 star-sectors each: the first list with the switches off, the first list with the current setting, and the second list's stored one-time search. Every event and every tier had to match the stored results.
5. **Two differences, found and explained.** In the third test two events were ranked lower in the stored run. A rule says an event is doubted if it has a partner at a whole number of binary orbits in another sector. Our test looked at one sector at a time, so it could not see the partner. The code was right; the test was too narrow. We widened the test and all three passed 300 of 300.
6. **Text size.** On a phone, a lot of labels, table headings and captions were 12 to 13 px. Everything readable is now at least 14 px, and a browser test fails the build if any readable text goes below that.
7. **A first reach map.** For each planet size and orbital period, how likely was the search to find it? It is an upper bound (a planted fake dip is easier than a real, wandering one), so it is labelled that way.

## The idea behind it

A fingerprint is a promise: the rules that made a result are exactly the rules we say made it. A refusal is the promise working. When it refuses, the wrong moves are to edit the fingerprint or to say the extra changes are probably harmless. The right move is to find exactly what differs, then re-run old results through the new code and look for any difference. When a test and the code disagree, find out which one is wrong before you change either.

## What we found, and what we did not

- **Found (CONFIRMED):** the new code reproduces the stored results exactly: 300 of 300 star-sectors in each of the three tests (661, 661 and 714 events).
- **Found (CONFIRMED):** the borrowed-time table covers 80% of the faint star-sectors that need a borrow with the pooled lists, against 1% with the third list alone.
- **Found (CONFIRMED):** the third list's stars are faint, so it tests large planets: in about two thirds of its star-sectors the smallest planet that reaches a signal of 7 in one crossing is above 10 Earth radii.
- **Not done:** the search on the third list. It waits for an explicit go.
- **Not tested:** whether the stated eclipse lengths in the third list's catalogue are full widths or narrower ones (UNCERTAIN; a small effect on one flag). **Later the same day (audit):** they are LIKELY full-width-like. Against the physics length, the third list's median is 0.50 and our first list's measured full widths give 0.38, so they are not narrower. Still not CONFIRMED, because the catalogue's own definition was not opened.

## Later the same day: what a public amateur package taught us

Ahmed asked what we can learn from Pavel Rabtsevich, who reported a planet candidate around the star TIC 4206066 using Claude Code and Codex. What is CONFIRMED: it is a candidate only, he claims no validation, and TESS watches the star from 31 October to 26 November 2026, so the real answer is still to come. We read his Research Note, his data package and his preregistration. Things he does that we do not do yet:

1. **A public, hashed prediction before the new data**, with four outcomes (recovered, inconsistent, excluded, insufficient). A missing signal counts as excluded only if the test would have caught it at least 95% of the time.
2. **A null built with the same machinery as the real test**, and a measured count of independent trials. That count made him widen his own printed limit.
3. **A second analysis in separate code by a different model.** Agreement between tools was not counted as proof.
4. **A map from every printed number to a file.**
5. **A wider check that the signal was not already known**, with a dated sentence.
6. **Frozen library versions**, so a run refuses to start in another setup.

What we do better: our search settings and a sealed set of stars are fixed before any result is seen, while his candidate was picked after looking, below his own shortlist threshold. None of the six is built yet; they are tasks T125 to T130 in the build queue (CONFIRMED from his files; the list of his 74 tests was not found). ## Questions

1. Why is a refusal to freeze good news?
2. Two events differed between the stored run and the new code. Why did we change the test and not the code?
3. Why borrow good time from the pooled lists instead of only the third list?

Answers: 1. It shows something changed that we had not noticed; a quiet override would have hidden it. 2. The events were ranked lower in the stored run because of a rule that needs a partner in another sector; the test only looked at one sector, so it was the test that was too narrow, and widening it made all 300 match. 3. A faint star's light curve needs good-time stretches from neighbours; the third list alone has too few neighbours (about 1% of cases) and the pool has enough (about 80%).
