## 2. Our own house first (done before the web; scripts in the scratchpad, numbers re-checkable)
- **Hidden input (I1), CONFIRMED by code reading:** a QLP-only star-sector gets its good-time windows from `audit_all.neighbour_windows`: the INTERSECTION of the good windows of every other star with SPOC-family light on the same sector, camera and CCD, read from `spoc_windows.pkl`, which the prep step rebuilds from ALL files in the set's data folder (`audit_all.py` lines 18 to 19 and 95 to 101). That pickle is overwritten at each prep, is not in the run's settings hash (the settings hold stars, manifest, targets, best_product and 11 code files, not the windows), and the 29 Oct version no longer exists. More stars in the folder means more windows intersected, so windows can only shrink. 2 Nov comparison: 77 of 583 neighbour-window groups changed; 2,651 own-window groups did not.
- **G3 consequence (the big one), LIKELY, to be measured after the download:** for G3 the pickle would be built from G3's own files only. G3 is 612 faint stars (median Tmag 12.8) with about 4 sectors each and mostly no 2-minute SPOC light, so many sector-camera-CCD cells will have none or one neighbour: `win_src` "NONE (unsafe)" or "ONE neighbour (weak)", and those QLP-only groups are dropped or weakened. The 895-star G2 set had a much denser cell population. This could cost G3 most of its QLP-only star-sectors.
- **Duplicated logic (I2), CONFIRMED by grep:** the tier rule is recomputed offline in `stage3_report.py`, `scorecard_plus.py`, `v9_study_analysis.py` (and two tests) besides `stage3_core.tier_of`; 99 scripts in `pipeline`, 18 non-test scripts read environment variables (`SS_SET` in 10 places, `VESPER_OPTS` in 3, `SS_RUN`, `SS_PROCS`, `PAIRED_FEATURES`), 5 write pickles, 16 read the group JSON files.
- **Comparability (I3):** the 29 Oct development run could not be used as a baseline; the fresh baseline cost about 45 minutes of machine time and the study analysis refused a verdict first (its machinery check). mistakes.md records 1 comparability entry so far (today's).
- **Switches, CONFIRMED:** 9 study switches exist in frozen code (bf4, c1a, c1b, c1c, c2, c6, dg, nd, fl); five were rejected by studies (bf4, c1a, c1b, c1c, c2) and stay in the code as dead options.

- **Determinism (Q7), CONFIRMED for the sample:** zero-difference test, 300 of 300 star-sectors identical to the frozen run with 8 workers on 2 Nov (the frozen run used another worker count); the chain files have no `parallel=True`, `prange` or `njit` (grep), so no cross-group reduction exists inside our files (wotan and numba internals were not audited).

Our manifest records none of this (columns: tic, author, file, bytes, path).

## 3. Findings by question (source, exact words, label, decision fed)
**Q1 cache keys.**
- Snakemake CLI reference: "Define what triggers the rerunning of a job. By default, all triggers are used, which guarantees that results are consistent with the workflow code and configuration." Choices: code, input, mtime, params, software-env. Also "List all output files for which the given items (code, input, params) have changed since creation." CONFIRMED (snakemake.readthedocs.io/en/stable/executing/cli.html). Feeds: the cache key = code + inputs + parameters + software environment, not timestamps; and a "what changed" report as a standing tool (I3).
- DVC internal files: "DVC calculates the file hash, a 32 characters long string (usually MD5)." and "The run cache assumes that stage commands are deterministic". CONFIRMED (doc.dvc.org/user-guide/project-structure/internal-files). Feeds: content hashes as identity; a cache is only valid if the step is deterministic, so determinism is a precondition we test (Q7) and re-audit on a sample of cache hits.
- Bazel hermeticity: when "given the same input source code and product configuration" a hermetic build "always returns the same output"; "Hermetic build systems use this hash to identify changes to [inputs]"; "If you run the same build step twice or on different systems, compare a hash of the file contents and get results that differ, the build is not reproducible" (fragments joined across line breaks). CONFIRMED (bazel.build/basics/hermeticity). Feeds: the repeat-and-compare check as the audit of the cache.
- Nx task sandboxing: "If a task reads a file that isn't listed in its inputs, the cache has no way to know that file changed, and it'll serve a stale result." "Undeclared dependencies are difficult to catch through code review alone. A task might work correctly for months until an unrelated change to an undeclared input causes a cache-related failure that's hard to trace back to the root cause." Detection: compare the file reads a task really makes with its declared inputs ("sandbox violation"). CONFIRMED (nx.dev/docs/features/ci-features/sandboxing). **This is item 70 exactly** and gives the detection practice: a read ledger per group compared with the declared inputs.
- Decision: do NOT adopt Snakemake, DVC, Bazel or Nx (a one-person project would carry more ceremony than the problem; the ideas are what we need). Home-made, about 150 lines when phase 1 comes. Label: my judgement (LIKELY).

**Q2 provenance in survey pipelines.**
- STScI Kepler CBV page: "As data is reprocessed, so will the CBVs. Be sure to use CBVs with the same Data Release number as your data." CONFIRMED (archive.stsci.edu/kepler/cbv.html).
- HEASARC TESS notice: "Users can refer to the data release number in the headers of the data files in order to distinguish between the new and original data files." and "Once the reprocessed data are ingested, MAST will only be making accessible the newer version of the light curve, target pixel and FFI files for each sector." CONFIRMED (heasarc.gsfc.nasa.gov/docs/tess/reprocessed-tess-data-coming-soon.html). Feeds: the same star can have different files later; record DATA_REL and PROCVER (SPOC family) and a sha256 (all files; QLP has nothing else).
- QLP Data Release Notes 004 (arXiv 2603.22236, HTML): the new TESS-Gaia photometry "is implemented as of Sector 94 in QLP light curves" and "We plan to reprocess all TESS data using the new TGLC photometry methods". CONFIRMED. Feeds: QLP products can change method by sector and be reprocessed: record hashes at download (G3 prereg already says files can change).

**Q3 shared-neighbour inputs.**
- STScI newsletter July 2025: "Starting in sector 48, an iterative Contrending Basis Vector (CBV) selection algorithm was added to the processing pipeline... the selection was too aggressive, resulting in a fewer basis vectors and a loss of photometric precision... Sectors 48-65 have now been reprocessed with the updated selection." CONFIRMED (archive.stsci.edu/contents/newsletters/july-2025/tess-sectors-48-65-reprocessed). Feeds: even SPOC's own shared-ensemble step (which other stars may define a correction) changed results for 18 sectors and was versioned and reprocessed; our windows table must be a versioned, hashed artefact built from a stated reference set, not a by-product of whatever is in a folder.

**Q4 switches, hidden state, tests.**
- Fowler, Feature Toggles: "Toggles introduce complexity... we should also aim to constrain the number of toggles in our system." and (toggle router) "This allows automated tests to verify both sides of a toggled feature". CONFIRMED (martinfowler.com/articles/feature-toggles.html). Feeds: retire the five rejected switches at the next freeze (zero-difference proof), keep the options recorded in every run (done 2 Nov), test both sides of each kept switch.
- Kanewala and Bieman, Testing Scientific Software (arXiv 1804.01954, abstract page): 62 studies; scientific software raises special testing difficulties. CONFIRMED for the abstract only; that "many test selection techniques assume a perfect oracle" and that metamorphic testing is a promising answer comes from a search summary of the paper: LIKELY, full text NOT OPENED. Feeds: our upside-down and mirror-bump tests are already metamorphic relations (a transformed input must give a predictable output); add cheap ones: time shift, flux scale, and **independence from other groups** (a group's events must not change when unrelated stars are added to the manifest; that test would have caught item 70).
- Wilson et al. 2017 (PMC5480810): "Record all the steps used to process data." CONFIRMED but generic. Sandve et al. 2013 (PLOS Comput Biol): "Rule 1: For Every Result, Keep Track of How It Was Produced"; the documentation "can easily get out of sync with how the analysis was really performed", so specify the workflow "in a form that allows for direct execution"; Rule 3: archive exact versions of external programs; Rule 6: note random seeds. CONFIRMED. Feeds: the run recipe is executable and records library versions and seeds.
- Sculley et al. 2015 (Hidden Technical Debt in Machine Learning Systems): NOT OPENED (PDF only; search summaries about undeclared consumers and configuration debt). UNCERTAIN: not used for any decision.

**Q5 comparability of variants.**
- Christiansen et al. 2020 (arXiv 2010.04796, abstract page): "By injecting simulated signals into the calibrated pixel data and processing those pixels through the pipeline as normal" the detection probability is measured. CONFIRMED (abstract). Our chain_recovery does the same through the whole chain; the full text was NOT OPENED (the HTML mirror was unavailable), so nothing about their comparison controls is claimed.
- Decision: a **recipe diff gate** before any comparison (code files, options, star list, manifest, targets, best_product, windows pickle, file versions, library versions): print what differs, refuse a verdict unless only the intended switch differs (the practice behind the Snakemake change listing and the hash comparisons above).

**Q6 speed.** wotan GitHub page: no timing figures (it recommends methods by noise type); the wotan and TLS documentation pages returned no matching text; the two papers' HTML mirrors were unavailable (HTTP 503). UNCERTAIN: no external speed evidence read. Own profile (section 2) says no hot spot. **No change** except the cache.

**Q7 determinism.** Numba parallel documentation: the fragments read say a reduction is inferred automatically and that "in the general case the result depends on the order" for some operations (the sentence was cut; not enough to cite). Search summaries on floating-point non-associativity: LIKELY, general knowledge. Own test (section 2) is the evidence. Feeds: 8 workers are safe on the sample; keep a standing zero-difference run (84 s) as the gate.

**Q8 connected status.**
- RO-Crate Process Run Crate: records the software used (SoftwareApplication with a version string, "RECOMMENDED to specify a machine-readable version string... to facilitate comparison attempts by consumers"), the execution (CreateAction), consumed inputs (`object`) and results, and a status for failed runs. MLflow Tracking: "logging parameters, code versions, metrics, and output files". CONFIRMED (spec and doc pages). Decision: borrow the vocabulary (job, run, declared inputs, outputs, software and versions, status), keep one plain JSON file per run that the Search window, the job list and the Downloads page read; adopt none of the three tools.
