Vigil survives all three gates in a smaller form. ## 2. V-B: statistics of looking every month

- **V-B1 answered, LIKELY.** Online false discovery rate methods exist: LOND and LORD ([Javanmard and Montanari, arXiv:1502.06197](https://arxiv.org/abs/1502.06197), abstract read), SAFFRON ([Ramdas et al., arXiv:1802.09098](https://arxiv.org/abs/1802.09098), abstract read), and their guarantee under "positive, local dependence" ([Fisher, arXiv:2110.08161](https://arxiv.org/abs/2110.08161), abstract read: LORD and SAFFRON were shown to control the traditional FDR only under an independence condition, now extended). All of them need p-values. **We have none:** Vesper's SNR comes from the measured scatter of the box statistic, the noise is red, and events cluster on stars. Decision for the protocol (my reasoning, not a source): do not claim a p-value or an FDR. A lead is a tier-1A real event on a non-known host; the false-lead rate is read from the upside-down control in the same files; an excess is claimed only through the cumulative star-level ratio with a star bootstrap (the method `scorecard_plus.py` already uses), never from one sector.
- **V-B2 answered, CONFIRMED on our data, with a limit.** Script `v_b2_control_wobble.py`, output `v_b2_control_wobble.txt`. Tier-1 events (1A, 1L, 1B) at SNR 7 or more, primary product, loaded without the c6 option, so counts differ from the scorecard's. **Sealed G2 run:** 86 sectors, 6,373 star-sectors, real 46, upside-down 53; upside-down rate 8.3 per 1,000 star-sectors; per-sector dispersion index 1.12 (1 = pure counting noise). **Development slice (0.7.1 run):** 95 sectors, 3,189 star-sectors, real 90, upside-down 24; dispersion index of the upside-down rate 2.28 (clustering on stars). The sealed control is consistent with Poisson noise; the development control is overdispersed. Limit: about 0.6 upside-down tier-1 events per sector, so **no single sector can say anything**. Plan change: Vigil publishes cumulative counts only; the lead rule and the null meter never use a one-sector comparison; uncertainty uses a star bootstrap, not Poisson.
- **V-B3 OPEN.** How multi-sector evidence turns into a lead. See V-B5 for the main fact (two events are needed to fix a period).
- **V-B4 answered, CONFIRMED on our table, LIKELY on the meaning.** Script `v_b4_period_ratios.py`. Planet period over binary period, known circumbinary planets with both periods in our tables (planet periods from `data/xmatch/cbp.csv`, binary periods from the Prsa 2022 table or our G1 list): Kepler-16 b 5.57, Kepler-38 b 5.62, Kepler-35 b 6.34, TOI-1338 b 6.53, Kepler-413 b 6.55, Kepler-47 b 6.64, PH1 b 6.92, Kepler-453 b 8.80, Kepler-34 b 10.39, Kepler-1660 b 12.87; 15 transiting-sized planets in all (period under 1,000 days), the rest much longer (Kepler-47 c and d 25 and 41, Kepler-1647 b 98). **Seven of the ten shortest sit between 5.6 and 6.9.** This also settles the Horizon floor question (section for RS-002). Plan change: a "linker" could look only for event pairs whose spacing is a multiple of about 5.5 to 7 binary periods; that is a prior from ten planets, UNCERTAIN, and the stacking decision stays with the 0.9 plan (no generic stacking).
- **V-B5 answered, LIKELY.** Own data: our scorecard (section E of `scorecard-plus-sealed.txt`) shows TOI-1338 b transit times moving by **+0.26 to +0.31 days (S27 to S68), +0.60 (S65) and +0.83 to +1.31 days (S89 to S98)** against the 2020 published epochs: a ledger window built from a 2020 ephemeris would need to be about +-1.3 days five years later. Literature: [Armstrong et al. 2013, arXiv:1307.1076](https://arxiv.org/abs/1307.1076) give an analytic limit on how far circumbinary transit times can move, "accurate to approximately 1% in predicting limits on possible times of transits over a three-year observing campaign" (abstract read; needs the planet period). [Kostov et al. 2020, arXiv:2008.02756](https://arxiv.org/abs/2008.02756): multiple transits in one conjunction give a period within "<10-20%" of the true value for low-eccentricity orbits (abstract read). For a planet of period near 100 days that is a window of 10 to 20 days wide, **too wide for a sharp prediction**. Conclusion: the prediction ledger only works for leads with two events (a period good to a few days). Plan change: ledger scope cut to two-event leads; single-event leads are tracked by the null meter only.

## 3. V-C: where it runs without his PC

- **V-C0 answered, LIKELY.** Latency does not matter for the results: MAST keeps the files, a run a week late finds the same data. What matters is only that a prediction is stamped before the data it predicts exists. A Windows Task Scheduler task with "run task as soon as possible after a scheduled start is missed" catches up after the PC was off, waiting 10 minutes by default per [Microsoft's Task Scheduler documentation](https://technet.microsoft.com/en-us/library/cc722178) (older Server 2008 R2 text, seen through a search summary, not opened). So **the PC-off problem is small**: a local monthly run with catch-up is enough for the science; cloud is a convenience for counting, stamping and alerting while the PC is off.
- **V-C1 answered for the main candidates, CONFIRMED.**

## 5. V-E: ledger and trust

- **V-E1 answered, CONFIRMED.** A git commit date is not proof of time: `git commit --date` and the `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` variables set them ([git-commit documentation](https://git-scm.com/docs/git-commit)). GitHub's events API carries `created_at` for push events but "event latency can be anywhere from 30s to 6h" and it is not built for real-time use ([GitHub events API](https://docs.github.com/en/rest/activity/events)); how long it keeps events was not confirmed. **OpenTimestamps** ([site](https://opentimestamps.org/)): free calendar servers, "no registration or api key", `pip3 install opentimestamps-client` then `ots stamp`; it anchors a hash in Bitcoin. Plan change: each month the hash of the ledger head is stamped with OpenTimestamps and the `.ots` proof is committed; the commit time is only a secondary witness. RFC 3161 time-stamp authorities were not checked.
- **V-E2 partly, LIKELY.** [RFC 8785 (JSON Canonicalization Scheme)](https://rfc-editor.org/rfc/rfc8785.html) fixes key order, no whitespace and number serialization, so the same record gives the same hash; it is an Informational RFC, and NaN and infinity are not allowed. Plan change: ledger records are canonical JSON per RFC 8785 or a documented subset; NaN is written as null before hashing. Details (genesis record, correction rule) open.

## 7. What changes in the plan (RS-001)

1. Vigil becomes a **monthly null meter** over new sectors, about a month behind, SPOC 2-minute and QLP only.
2. **Local run with catch-up is the base;** the cloud job (GitHub Actions) is optional and only counts, stamps and alerts, with leads recomputed locally.
3. **No p-value or FDR claims;** cumulative star-level ratio with a star bootstrap; one sector is never evidence.
4. **Prediction ledger only for two-event leads.**
5. Every input file is hashed; the QLP method era (before and after S94) and the QLP correction are recorded.
6. Monthly ledger head is stamped with OpenTimestamps.
7. Keep-alive for the 60-day rule if GitHub Actions is used.
8. Protocol ends if TESS ends (planned to Sept 2028; EM3 funding UNCERTAIN).
